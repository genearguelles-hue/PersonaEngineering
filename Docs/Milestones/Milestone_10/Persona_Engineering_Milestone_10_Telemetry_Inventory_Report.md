## 1. Purpose

This report consolidates the token-telemetry inventory conducted across the three repositories that support Persona Engineering Milestone 10:

1. `PersonaEngineering`
2. `pe-mission-control`
3. `token-governance`

The inventory determines:

- what token-related evidence already exists;
- whether each source is provider-reported, locally estimated, simulated, proxy-based, or structural only;
- whether governed and ungoverned observations can be paired;
- whether governance overhead can be attributed separately;
- which artifacts may be used for calibration;
- what must be implemented before the final Milestone 10 experiment begins.

This report is an evidence inventory and readiness assessment. It is not the final Milestone 10 experimental protocol or findings report.

---

## 2. Executive Determination

The three repositories contain a substantial foundation for Milestone 10, but they do not yet contain a final mission-level governed-versus-ungoverned token dataset.

The strongest existing empirical token evidence is the corrected report-generation pilot v1.0.1 in `PersonaEngineering`. It contains two valid matched `persona`/`no_persona` pairs with provider-reported token usage and blinded quality assessment. Across those pairs, the persona condition consumed 181 more report-generation tokens than the no-persona condition, an increase of 3.86%, while mean quality was 0.05 points lower.

That result is valid calibration evidence, but it is not a full Persona Engineering governance comparison. The pilot isolates the effect of a persona instruction fragment during report generation. It does not measure the complete mission effects of:

- authorization;
- policy evaluation;
- orchestration;
- context retention;
- repair and retry loops;
- drift prevention;
- tool selection;
- evidence normalization;
- Assessor activity;
- Ledger processing;
- manifest sealing.

The `pe-mission-control` runtime provides strong governance and evidence integrity, but it is governed-only and its imported token fields are unpopulated for the inspected deterministic Selenium and JMeter missions.

The `token-governance` repository provides a mature synthetic Monte Carlo research model and empirical response comparisons based on word and character counts. It does not yet provide provider-reported token telemetry for complete governed and ungoverned missions.

**Readiness decision:** Milestone 10 may proceed to protocol and instrumentation design, but the final comparative execution campaign must not begin until the paired observation path and token-attribution controls pass a pilot.

## 4. Evidence Classification Standard

| Class | Definition | Permitted Milestone 10 use |
|---|---|---|
| A — Provider-reported | Usage returned by the model provider for the actual request | Calibration or final evidence if pairing and mission controls also pass |
| B — Tokenizer-derived | Counts reproduced locally with the correct model tokenizer | Secondary evidence; must be labeled and reconciled with provider usage |
| C — Locally estimated | Approximation such as characters divided by a constant | Historical or exploratory analysis only |
| D — Proxy measurement | Words, characters, latency, turns, or related non-token measures | Supporting analysis; not a token-consumption claim |
| E — Simulated | Values generated by a statistical or Monte Carlo model | Hypothesis formation, sensitivity analysis, and experimental design |
| F — Structural placeholder | Schema fields or runtime properties with no populated observation | Instrumentation foundation only |
| G — Documentation | Requirements, plans, formulas, or narrative claims | Methodological context only |

Evidence classes must remain separate in the final dataset and findings report.

## 5. Repository Findings

## 5.1 `PersonaEngineering`

### 5.1.1 Corrected report-generation pilot v1.0.1

The corrected pilot is the strongest existing empirical token artifact.

**Artifact:**  
`reports/experiments/report_generation_v1/pilot_v1_0_1/pilot_results_v1.0.1.json`

**Experimental properties:**

- model: `gpt-5.4-2026-03-05`;
- four report-generation requests;
- two valid matched pairs;
- provider-reported input and output tokens;
- blinded assessment;
- deterministic validation;
- no invalid pairs;
- status: `complete`.

### Aggregate result

| Condition | Report-generation tokens | Mean blinded quality | Quality-adjusted token efficiency |
|---|---:|---:|---:|
| No persona | 4,689 | 4.95 | 2.111324 |
| Persona | 4,870 | 4.90 | 2.012320 |
| Persona minus no persona | **+181** | **−0.05** | **−4.69%** |

The persona condition used 3.86% more report-generation tokens:

`181 / 4,689 = 0.038601`

### Pair-level result

| Pair | No-persona tokens | Persona tokens | Token delta | Quality delta |
|---|---:|---:|---:|---:|
| Selenium QA report | 1,702 | 1,793 | +91 (+5.35%) | 0.0 |
| JMeter performance report | 2,987 | 3,077 | +90 (+3.01%) | −0.1 |

**Classification:** Class A provider-reported calibration evidence.

**Restriction:** The experimental labels are `persona` and `no_persona`, not full `governed` and `ungoverned` mission conditions. The result must not be cited as a complete Persona Engineering token-savings test.

### 5.1.2 Original report-generation pilot

The original pilot recorded provider-reported token usage, but only the Selenium pair was valid. The JMeter pair reached the configured output limit and returned incomplete provider status in both conditions.

**Classification:** Class A failed-pilot and calibration evidence.

**Permitted use:** Demonstrating why completion status, truncation controls, and pair-level validity gates are mandatory.

### 5.1.3 General Selenium and JMeter envelopes

The test-run schema and runtime envelopes include:

- `prompt_tokens`;
- `completion_tokens`;
- `total_tokens`;
- `estimated_usd`;
- `token_usage_available`.

In the inspected Selenium and JMeter run records, these fields are `null`, and `token_usage_available` is false. The inventory exposed 20 indexed test runs, predominantly governed, with one ungoverned Selenium run. They do not form a controlled matched token dataset.

The null token values are not inherently erroneous. Selenium and JMeter execution is deterministic and may make no model call. The schema currently fails, however, to distinguish clearly among:

- no LLM call occurred;
- an LLM call occurred but usage was unavailable;
- instrumentation failed;
- the metric is not applicable.

**Classification:** Class F structural placeholders.

### 5.1.4 Token Assessor and token-burn report

The deterministic Assessor estimates tokens using character counts and a fixed characters-per-token approximation. The historical token-burn report aggregates these estimates and compares them with a theoretical baseline.

The observed historical aggregate of approximately 8,500 governed tokens versus 8,641 theoretical ungoverned tokens represents an estimated reduction of about 1.63%.

**Classification:** Class C locally estimated evidence.

**Restriction:** It cannot serve as empirical proof of token savings.

### 5.1.5 Existing schema

`schemas/infrastructure/token-telemetry.v1.schema.json` is a strong starting point for Milestone 10 D10.2.

**Classification:** Class F structural foundation.

**Required action:** Extend or supersede it only through an explicit versioned schema change. Do not silently change the meaning of existing fields.

## 5.2 `pe-mission-control`

Mission Control has already proven the following Milestone 9 capabilities:

- contract validation;
- pre-execution authorization;
- governed Selenium and JMeter execution;
- deterministic policy evaluation;
- Persona Assessor execution;
- hash-chained Ledger recording;
- evidence manifest sealing;
- independent verification.

The inventory nevertheless identifies the following Milestone 10 constraints:

| Capability | Inventory result |
|---|---|
| Governed execution | Implemented |
| Ungoverned experimental condition | Not supported |
| Runtime mode validation | Requires `governed` |
| Pair identifier | Not found |
| Provider token capture | Imported fields only; inspected values are null |
| Governance-overhead attribution | Not implemented |
| Identical sealing of both conditions | Not implemented |
| Evidence integrity | Implemented and verified |

The completed governed JMeter mission correctly contains null token fields because its tested execution path did not itself make an LLM request.

**Classification:** Governance runtime and Class F instrumentation foundation.

### Architectural implication

Mission Control must not simply weaken its governed-only validation to admit an ungoverned run. Milestone 10 requires a neutral experimental observation layer that can:

1. execute or observe both conditions;
2. preserve the distinction between authorized governance and experimental bypass;
3. seal both conditions with equivalent evidence controls;
4. prevent an ungoverned condition from being mislabeled as authorized;
5. attach both records to one immutable `pair_id`.

The observation plane may be neutral; the governance semantics must remain explicit.

## 5.3 `token-governance`

### 5.3.1 Monte Carlo framework

The repository contains a mature Monte Carlo model comparing governed and ungoverned token consumption across three mission classes:

- short-horizon determinate;
- long-horizon determinate;
- nonlinear human-centered.

The simulation models:

- context tokens;
- output tokens;
- tool tokens;
- governance tokens;
- repair loops;
- rebrief events;
- context relevance and waste;
- unnecessary tool use;
- total token burn.

Governance overhead is an explicit modeled variable. The simulation and its calibration batches are useful for hypothesis development, power analysis, sensitivity analysis, and defining expected failure modes.

**Classification:** Class E simulated evidence.

**Restriction:** Monte Carlo trial rows are synthetic samples from assumed distributions. They cannot be combined with provider-reported observations as though they were measurements of live missions.

### 5.3.2 Financial Guidance governed/ungoverned demo

The Financial Guidance demo contains actual generated-response comparisons and heuristic assessments. It records word counts, character counts, behavioral scores, and drift flags.

Examples from the two inspected three-prompt assessments include:

| Assessment | Avg governed words | Avg ungoverned words | Avg governed characters | Avg ungoverned characters | Avg overall score, governed / ungoverned |
|---|---:|---:|---:|---:|---:|
| 2026-04-17 16:15:33 | 308.7 | 270.0 | 2,006.3 | 1,795.0 | 4.33 / 4.33 |
| 2026-04-17 16:50:08 | 245.7 | 257.0 | 1,574.0 | 1,722.7 | 4.33 / 4.00 |

These results demonstrate that governance effects may be mixed by prompt: governed output may be shorter or longer, and behavioral quality may improve, remain equal, or decline under particular heuristic dimensions.

**Classification:** Class D proxy measurement with behavioral assessment.

**Restriction:** Word and character counts are not provider-reported token usage. These records should be retained as historical calibration examples, not final token evidence.

## 7. Precise Instrumentation Gap

Milestone 10 does not lack a token-count field. It lacks a complete causal measurement envelope connecting token usage to a controlled mission pair.

The required gap closure consists of the following.

### 7.1 Experimental identity

Every final observation must carry:

- `experiment_id`;
- `protocol_version`;
- `mission_class`;
- `mission_spec_id`;
- `pair_id`;
- `condition`;
- `run_id`;
- `attempt_id`;
- randomized execution order;
- seed, where applicable.

### 7.2 Condition semantics

The final protocol must distinguish:

- `governed`: the defined PE governance stack is active;
- `ungoverned`: the same mission is executed without the experimental governance mechanisms being tested;
- `persona`;
- `no_persona`;
- `tool_only`;
- `not_applicable`.

`persona/no_persona` must not be treated as a synonym for `governed/ungoverned` unless the protocol explicitly defines the persona fragment as the sole treatment.

### 7.3 Provider usage

For each LLM request, record the provider-reported fields available for that provider and model, including:

- input tokens;
- cached input tokens;
- cache-write tokens, if available;
- output tokens;
- reasoning tokens, if available;
- total tokens;
- provider completion status;
- model and immutable model version;
- request latency;
- pricing-table version.

Tokenizer-derived or estimated fallback values must be stored in separate fields with their method and confidence. They must never overwrite provider-reported fields.

### 7.4 Phase attribution

Token usage must be attributable to at least:

- mission work;
- persona/context injection;
- policy evaluation;
- planning/orchestration;
- Assessor evaluation;
- repair or retry;
- rebrief/context reconstruction;
- reporting;
- other governance overhead.

The sum of phase totals must reconcile with the request-level and mission-level totals.

### 7.5 Mission outcome and efficiency

Every observation must include:

- mission success or failure;
- quality score and assessment version;
- critical defect status;
- number of turns;
- tool calls;
- failed tool calls;
- repair loops;
- retries;
- human interventions;
- context carried forward;
- completion status;
- invalidation reason.

This supports cost per successful mission rather than cost per isolated response.

### 7.6 Deterministic and tool-only execution

Tool-only missions must explicitly record:

- whether an LLM was invoked;
- `token_applicability`;
- zero tokens when a verified zero is semantically correct;
- null only when the value is unknown or unavailable;
- a reason code for every null measurement.

This prevents valid zero-token deterministic execution from being confused with telemetry failure.

### 7.7 Equivalent evidence controls

Both conditions must receive equivalent:

- artifact capture;
- timestamps;
- hashes;
- manifest sealing;
- schema validation;
- pair registration;
- post-run validity checks.

The ungoverned condition may omit the governance treatment, but it must not omit measurement integrity.

## 8. Data Admissibility Rules

A matched pair may enter the final Milestone 10 analysis only if:

1. both conditions implement the same frozen mission specification;
2. the model and model version match;
3. sampling parameters and tool availability match;
4. execution order is recorded and randomized or counterbalanced;
5. both provider responses are complete;
6. provider-reported usage is present, or an approved protocol exception applies;
7. both outputs pass schema and artifact validation;
8. quality assessment is blinded to condition;
9. neither output has an unresolved critical defect;
10. phase totals reconcile with mission totals;
11. the `pair_id` is unique and present on both observations;
12. invalidation rules were defined before results were inspected.

Invalid pairs must remain preserved with explicit failure reasons. They must not be silently deleted or selectively rerun.

## 9. Claims Boundaries

The current evidence supports the following statements:

- Persona Engineering already has provider-reported token instrumentation in a small report-generation pilot.
- In that pilot, persona prompting created a small token overhead without a quality improvement.
- Mission Control can authorize, execute, assess, record, seal, and independently verify governed missions.
- Existing general Selenium and JMeter envelopes do not contain token measurements.
- Token Governance has a mature synthetic model and non-token empirical proxies.
- A mission-level governed-versus-ungoverned empirical comparison has not yet been completed.

The current evidence does **not** support the following statements:

- Persona Engineering has empirically proven mission-level token savings.
- The Monte Carlo percentage reductions are observed production savings.
- Persona prompts alone reduce token consumption.
- Deterministic Selenium or JMeter execution provides evidence of LLM token savings.
- Word or character reductions are exact token reductions.

## 12. Final Determination

The Milestone 10 foundation is stronger than an empty experimental start: Persona Engineering already possesses real provider telemetry, an A/B generation harness, deterministic quality controls, mature governed mission execution, verifiable evidence sealing, historical governed/ungoverned demos, and a calibrated Monte Carlo research model.

These pieces are not yet a single experiment.

The central Milestone 10 engineering task is to connect them through a versioned paired-mission observation model that preserves condition semantics, attributes governance overhead, captures actual provider usage, and seals both governed and ungoverned evidence to the same standard.

**Authorization to begin final experimental runs:** Not granted.  
**Authorization to draft D10.1 and design D10.2–D10.3:** Granted.
